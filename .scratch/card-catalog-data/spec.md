# Card Catalog and Rules-Ready Data

Status: ready-for-agent

This specification covers local set-code imports, card-name resolution, and a comprehensive data model aligned with Magic's Comprehensive Rules. It defines data that can support future rules automation; the initial Manual Match stores that data without executing card mechanics.

## Problem Statement

Players need to import Decklists using a known local card pool and play without depending on a live card service. A simple lookup schema is not enough for the long-term goal: cards have multiple faces, contextual characteristics, structured abilities, and relationships to Match state. If those distinctions are not represented early, later mechanics will require avoidable data-model changes.

At the same time, the first playable release is a Manual Match. Its data must be complete enough to grow toward rules automation while leaving the actual evaluation of mechanics to later work.

## Solution

Provide a maintainer command that imports one Scryfall set at a time by set code and stores the result locally. Begin with one selected set. Use a comprehensive game-specific model for card identity, characteristics, abilities, effects, and rules-related Match data. The long-term catalog target is the full Scryfall card pool. Maintain the full Card Name Directory separately from per-set imports so card-name choices can resolve even when a corresponding Card Definition is not yet eligible for a Decklist.

All successfully imported cards can be used in Manual Matches. Preserve their rules text and structured rules data, but do not evaluate abilities or effects in the initial version. Keep Catalog availability separate from future Rules-Automated Match coverage.

## User Stories

1. As a maintainer, I want to import a set by entering its set code, so that I can add a known card pool without downloading the entire catalog first.
2. As a maintainer, I want to import one set per command, so that the first setup can use a single set and the local catalog can grow incrementally.
3. As a maintainer, I want importing the same set again to be idempotent, so that retrying an import does not create duplicate Card Definitions, Card Printings, or directory entries.
4. As a maintainer, I want a failed fetch to leave the most recent successful catalog data intact, so that a provider outage cannot corrupt cards already available to Decklists and Matches.
5. As a player, I want Decklist text import to resolve every card against locally imported Card Definitions, so that a successful list contains no unresolved names.
6. As a player, I want the whole Decklist import rejected when an entry is unresolved or outside the imported set pool, so that an invalid list cannot be partly accepted.
7. As a player, I want to identify a card by its canonical name even when it has multiple printings, so that printings do not create duplicate gameplay identities.
8. As a player, I want an unspecified printing to resolve to one designated default printing, so that Decklist text can omit set details.
9. As a player, I want to optionally select an exact printing when a Decklist entry includes set code and collector number, so that a list can retain a chosen version while printings of the same Oracle identity use one Card Definition.
10. As a player, I want card-name choices to resolve through a full Card Name Directory that is independent of set imports, so that a card can name a rules-recognized card, face, or alternate form before that card is locally importable.
11. As a player, I want a directory match not to make an unimported Card Definition eligible for Decklist import, so that name lookup does not bypass the local card-pool boundary.
12. As a card-data author, I want each Card Definition and Card Component to use the same complete Card Characteristics field model, so that ordinary cards and unusual card forms do not need separate ad hoc schemas.
13. As a card-data author, I want a simple creature with no abilities to use ordinary Card Characteristics and an empty ability collection, so that the model does not require a special case for vanilla cards.
14. As a card-data author, I want a context-specific alternate form to use Alternative Characteristics, so that values that apply only in a particular rules context remain separate from the card's normal Card Component.
15. As a card-data author, I want each Alternative Characteristics record to declare whether it is partial or full, so that inherited characteristics and absent characteristics follow the Comprehensive Rules.
16. As a future rules-engine author, I want Card Abilities represented with structured triggers, conditions, costs, modes, targets, choices, variable values, effects, and contextual references, so that later behavior can consume card data without re-parsing rules text.
17. As a future rules-engine author, I want printed keywords to link to their constituent Comprehensive Rules abilities, so that a keyword with multiple rules-defined abilities can retain each ability's applicable Zones and behavior.
18. As a future rules-engine author, I want ability origin and shared ability relationships recorded, so that printed, granted, and rules-derived abilities, including conditional card structures, can be understood without duplicating rules data on every card.
19. As a future rules-engine author, I want effects represented as ordered typed data, so that one-shot, continuous, replacement, prevention, and delayed behavior can be modeled without treating rules text as executable code.
20. As a future rules-engine author, I want characteristic checks and object relationships to retain their rules context, so that data can distinguish current information, last known information, an Attachment, and an Object Link.
21. As a Manual Match participant, I want casting choices, variable bindings, face choices, face-down information, and Object Links stored with the relevant Game Object, so that we can administer card behavior manually and later automation can read the same state.
22. As a future rules-engine author, I want immutable Copiable Values records to capture copy exceptions at copy time, so that a copied Game Object does not depend on later changes to its source.
23. As a player using cards with stickers, I want Sticker Sheets, Sticker Definitions, and placements stored separately from base Card Characteristics, so that sticker mechanics do not add specialized fields to every card.
24. As a player, I want predefined token data reusable independently of Card Definitions, so that token-creation effects can refer to shared token characteristics while each created token remains a Game Object without a Card Instance.
25. As a player, I want nontraditional objects and their required Zones or supplementary decks representable, so that a Manual Match can record them without requiring their variant procedures to be automated.
26. As a future rules-engine author, I want Catalog availability distinct from rules coverage, so that every locally imported card is usable manually while automated play can grow in stages toward full card coverage.

## Implementation Decisions

### Import, identity, and lookup

- Scryfall is the initial import and update source. Reviewed Card Catalog JSON files in Git are the runtime catalog; Matches do not perform live card lookups.
- A maintainer command accepts a set code and imports one set at a time. The initial catalog may contain one set. Further sets can be added using the same command.
- Re-importing a set is idempotent. Import into a temporary or otherwise recoverable state so a failed fetch or failed import preserves the last successful catalog state.
- A Card Definition is joined across imported printings by Oracle identity when Scryfall supplies it; its canonical name remains the Decklist label. A printing retains its own identity. Special layouts without a card-level Oracle ID need explicit identity mapping.
- Each Card Definition has one Git-tracked JSON file keyed by Oracle identity. It retains selected current Oracle gameplay fields, including Oracle text, and separately maintained primitive-based ability data. A set import updates only the imported fields in affected card files while preserving authored ability data and creates a placeholder marked `unimplemented` for a new Oracle identity. Its machine-queryable automation status is binary: `unimplemented` or `implemented`; incomplete work remains `unimplemented`, and a reviewer sets `implemented` explicitly rather than inferring it from a nonempty ability list. Card-specific behavior composes reusable engine primitives in JSON, while a missing primitive is added to shared engine code. A Card Printing records a specific set version, collector number, and artwork; one designated default Card Printing is used when a Decklist does not name an exact imported printing. Do not model gameplay-characteristic overrides between printings.
- For multi-faced cards, the front-face name is the canonical Decklist identity. Other face names can be directory names, but are not Decklist aliases.
- Decklist resolution requires the Card Definition to be present through a locally imported set. If a line specifies a printing, that exact Card Printing must also be imported. If it does not specify one, resolve to the default among locally imported printings. Reject an import containing any unresolved or out-of-set entry.
- Make the full Card Name Directory available independently of per-set Card Definition and Card Printing imports from the initial release. It includes every canonical, alternate, face, or composite name that a card-name-choice effect may legally select under the Comprehensive Rules. Entries can refer to a Card Definition, Card Component, Alternative Characteristics, or composite form. Set imports may add directory entries missing from the independent index. Directory membership does not imply Decklist eligibility.
- A chosen card name stored during a Match may be any name, including a name absent from the Card Name Directory and local Card Catalog. A chosen value does not create a Card Definition or Deck Entry.
- Card Definition stores Color Identity as a rules-defined property distinct from current color.

### Shared card characteristics

- Use a comprehensive game-specific schema aligned with the Comprehensive Rules, rather than treating Scryfall's schema as the domain model. Preserve source rules text alongside normalized structured data.
- Card Characteristics are the complete characteristic data for a Card Component or Alternative Characteristics record. Include every applicable rules characteristic and card-specific value: name, mana cost, colors and color indicator, supertypes/types/subtypes, rules text and abilities, power, toughness, loyalty, defense, and any other characteristic required by a card form. Represent fields that do not apply as absent rather than inventing a value.
- The first import retains Oracle identity, canonical name, layout and faces, Oracle text, keywords, mana cost and mana value, parsed supertypes/types/subtypes, colors and color identity, and applicable power, toughness, loyalty, and defense. It retains printing identity, set, and artwork link separately. Prices, rankings, vendor links, and cosmetic printing fields are outside this first gameplay import.
- Preserve applicable printed card data in addition to the rules characteristics, including symbols, quantities, and card-form metadata needed to import and identify the printing. A single-faced creature without abilities still has ordinary Card Characteristics and an empty ability collection.
- Each Card Definition has one or more Card Components. A Card Component contains the same Card Characteristics field model for each face or component; typed relationships describe how components form double-faced, split, Room, and other multi-part cards.
- Record double-faced form as modal double-faced, nonmodal double-faced, or meld, and store full Card Characteristics for every printed face. The Match stores the current face and records a chosen face when the card is cast or played as a land. Face selection and changes are manual initially.
- A melded form combines two Card Instances into one Game Object and uses the composite characteristics required by the Comprehensive Rules. The two Card Instances keep their identities and Owners.
- Model context-specific characteristics in a linked Alternative Characteristics record using the same field model. Each record declares a composition mode:
  - **Partial** alternatives supply changed values and inherit values from the linked Card Component where the Comprehensive Rules say those values remain unchanged. Prototype is the representative case.
  - **Full** alternatives provide the complete characteristics used in their stated context. Omitted values are absent rather than inherited. Adventure and Omen spells on the Stack, and characteristics of a Preparation spell copy, are representative cases.
- Store a typed relationship that states when and how Alternative Characteristics apply. For example, a vanilla creature has just its ordinary Card Component and no ability records; Phyrexian Fleshgorger's Prototype form is a partial Alternative Characteristics record for its changed mana cost, color, power, and toughness, inheriting its unchanged types and abilities.
- A Card Definition can carry computed characteristic values through a characteristic-defining Card Ability. Keep printed markers such as Tarmogoyf's `*` and `1+*` in Card Characteristics; the ability declares the value sources and the affected characteristics. Do not add reverse references from the printed stat fields to ability formulas.
- Store mana symbols and quantities as ordered typed values in mana costs, ability costs, and mana-producing effects, alongside rules text.

### Card Abilities and effects

- A Card Ability has a kind and applicable structured data for its trigger, condition, cost, mode, target, variable value, choice, replacement behavior, delayed triggered ability, effect, and references to Card Catalog or Match context. Printed abilities correspond to the Card Definition's Oracle text without requiring the text to be copied into every ability record. Not every field applies to every ability.
- Triggered abilities distinguish event triggers from state triggers and store the corresponding event or game-state condition. Manual Matches do not evaluate the trigger.
- Preserve ability origin as printed, granted, or rules-derived. Imported keyword names are source facts, not proof that their behavior is automated. Keywords such as flying, haste, ward, and trample use the shared Card Ability model; shared engine logic can handle a keyword only when its typed costs, conditions, and effects are represented and supported. A printed keyword can link to separate structured Card Ability records for each ability defined by the Comprehensive Rules; retain each ability's applicable Zone and behavior. Reuse rules data for abilities derived from characteristics rather than duplicating the same ability on every Card Definition. This includes intrinsic mana abilities of the five basic land types and reusable Saga lore-counter and sacrifice behavior.
- Preserve relationships among abilities represented together by a Comprehensive Rules construct: Class level bars and their activated/static parts, Leveler and Station thresholds and resulting abilities or characteristic changes, and a Case's “To solve” trigger, solved designation, and solved ability.
- Saga chapter numbers belong to their separate structured chapter abilities. Grouped chapter symbols remain separate abilities, and the final chapter number is derived from the greatest applicable chapter number.
- Variable Value Source is declarative data describing the source, references, parameters, and Comprehensive Rules timing for determining a value. It is not an executable function call. Store a determined value as a binding such as `X = N` on the relevant Game Object or Ability Game Object when applicable. Card Ability data may reference Match context, including the current Controller's Commander and that Commander's Color Identity.
- Use Effect in its Comprehensive Rules sense. Preserve rules text and represent effects as ordered structured parts. Distinguish one-shot, continuous, replacement, and prevention effects, as well as delayed triggered abilities created by an effect. Parts can reference Game Objects and characteristics using the required current-information or last-known-information timing.
- A Continuous Effect stores source ability, affected Game Objects or an Object Filter, typed semantic changes, value sources, duration, and applicability. Keep the effect separate from the recipient's printed Card Characteristics. Do not store Comprehensive Rules layer or sublayer labels in card data; future rules automation derives layer classification from each typed change's meaning.
- Model granted abilities and other continuous changes as effect data linked to their source and recipient. A grant does not rewrite the recipient's printed Card Characteristics. Applicability may depend on an Attachment or other Match relationship.
- Object Filter is a reusable eligibility predicate over possible Game Objects, including object kind, characteristics, Zone, and relationships to Match Players. It does not dictate when characteristics are checked.
- Zone Change Condition is shared data for replacement and triggered abilities. It identifies the moving object, source and destination Zones, and whether the move would occur or has occurred; it may refer to an Object Filter. Store the replacement action separately from the condition, and store a triggered ability's effect separately from its trigger condition. Put pre-change or last-known-information timing at the ability/effect use site. Do not add a Match event history or generic event snapshot to support these records.
- Object Links associate a source Game Object, optionally its Card Ability, with related Game Objects that an effect refers to. Keep Object Links separate from Attachments.
- Library Sequence is a reusable declarative effect group for inspecting successive cards from a Library. It records the source Zone, operation, stop predicate, handling and ordering of the selected card and remaining cards, and no-match behavior.

### Match data supported by the model

- Keep Card Definition, Card Printing, Card Instance, Game Object, Owner, Controller, and Zone as distinct concepts. A Card Instance represents one copy in a Match and retains its Owner. A Game Object is the current Match entity; it can represent a card, token, ability, emblem, or another supported nontraditional object and may reference one or more Card Instances or none.
- Store a spell's Casting Record on its spell Game Object. Capture its source Zone and applicable choices and payment facts, including chosen X, modes or fused split-card halves, alternative/additional costs, and colors of mana spent. Keep the record available as the spell resolves into a permanent or another Game Object needs the information. An object put onto the Battlefield without being cast has no Casting Record. Manual Matches record this data without validating or interpreting it.
- Represent Opening-Hand Actions in Card Ability data with applicable conditions, choices, costs, and actions. Match setup records whether each action was taken after mulligans and before the first turn and its result. Participants perform the action manually.
- A Face-Down State stores the underlying Card Instance or source object when applicable, face-down source or mode, characteristics shown while face down, applicable turn-up procedures, and who may inspect the underlying identity. Match views redact identity from participants without permission. Manual Matches do not evaluate face-down procedures.
- Store applicable Rules State (statuses and designations) as typed variants with their own value shape and applicability. Keep counters separate. Manual Matches can record state without enforcing its rules.
- A Battle Game Object records its Protector as a Match Player reference, distinct from its Owner and Controller. Manual Matches store the chosen Protector without enforcing eligibility rules.
- Capture Copiable Values, including copy exceptions, in an immutable record using the shared Card Characteristics field model. A copied Game Object references the captured record and does not depend on the original object's later state. Identical copies may share the same record; different exceptions require distinct records. Keep each Game Object's counters, status, Attachments, and other Match data separate.
- Provide reusable Token Definitions for all predefined tokens in the Comprehensive Rules, separately from Card Definitions, using the applicable Card Characteristics and Card Component structures. Token-creation effects can reference the definition and retain effect-specific additions or modifications. Custom tokens can use explicit characteristics or copy-based descriptors. A token is a Game Object without a Card Instance.
- Represent the nontraditional objects, special Zones, and supplementary decks needed for manual play, including emblems, Dungeons, planes, phenomena, conspiracies, Attractions, and Contraptions. Special game areas can hold multiple active objects of the same kind where a variant permits it, including multiple active Planes for Spatial Merging. Players handle their mechanics and procedures. Do not implement Scheme or Vanguard variant support.
- Store Sticker Sheets and Sticker Definitions separately from Card Definitions, Card Components, and Card Characteristics. Sticker Definitions retain their rules-relevant kind and printed value, including ticket cost when applicable; an ability sticker may refer to shared Card Ability data. Match state records which sheets each Match Player can use and each ordered Sticker Placement on a Game Object. Do not add sticker-specific properties to the base card record or automate sticker selection and effects initially.
- Support the described card rules structures and Match references in the data model. Imported Card Definitions may begin with unimplemented ability placeholders, and authored behavior grows card by card. Do not implement card mechanics, calculate derived characteristics, evaluate triggers, or apply effects in Manual Matches.
- Keep Catalog availability independent of automation coverage. A Manual Match can use every imported card. Any future Rules-Automated Match identifies supported cards and mechanics; unsupported cards remain usable manually. The long-term goal is the full Scryfall card pool with rules support for every card. Initial automated coverage can begin with lands producing mana and spells spending mana, then expand to cost increases, cost reductions, keywords, and interactions.

## Testing Decisions

- Test behavior through the importer and the Card Catalog data consumers, not private parsing functions or a particular database shape. Verify the resulting local data can be used by Decklist resolution and Match-facing card records.
- Use one Card Catalog integration/contract seam: import a set by code, inspect its locally available cards and structured records through their consumers, re-import it, then simulate a failed import and verify the last successful data remains available.
- Verify Decklist resolution accepts only canonical names for locally imported Card Definitions, resolves an optional exact printing only when that printing was imported, uses the designated default when omitted, and rejects the entire text import if any entry is unresolved or out of set. Verify Card Name Directory lookup remains independent of that eligibility rule and supports alternate and composite names.
- Validate model breadth with representative data rather than relying only on ordinary card examples. Include a simple creature with no abilities; multi-color and multi-face cards; split, Room, meld, Adventure, Prototype, Omen, and Preparation forms; keyword abilities with multiple rules-defined parts; triggered and state-triggered abilities; characteristic-defining values; continuous, replacement, prevention, and one-shot effects; tokens; nontraditional objects; stickers; and named choices.
- Verify concrete rules-data relationships: Tarmogoyf's printed `*` and `1+*` plus its characteristic-defining ability; Walking Ballista's printed 0/0, chosen X, and counters; separate Saga chapter abilities; a Flashback keyword's Graveyard casting permission and Stack replacement ability; Progenitus's would-move replacement versus Emrakul, the Aeons Torn's completed-move trigger; Blood Artist's pre-zone-change creature check versus Scavenging Ooze's last-known-information check; Leyline of the Void and Rest in Peace with distinct Object Filters; and Opalescence/Humility changes without layer labels.
- Verify Alternative Characteristics composition with Phyrexian Fleshgorger's partial Prototype values and Bonecrusher Giant's full Stomp alternative. Verify Omen spell and Preparation spell-copy characteristics as full alternatives. Confirm a simple creature's ordinary Card Component does not require an Alternative Characteristics record.
- Verify immutable Copiable Values with Phyrexian Metamorph and Reflection of Kiki-Jiki, including their copy exceptions: a captured copy must not change when its source changes or leaves, and separate exceptions produce separate records.
- Verify Casting Records retain source Zone, choices, costs, and spent mana colors through spell resolution where needed; verify an object put directly onto the Battlefield has no Casting Record. Verify Opening-Hand Actions are recorded after mulligans without automated eligibility enforcement.
- Verify private Match views redact unauthorized face-down identities while retaining the underlying object reference and turn-up data for authorized participants. Verify attachments, Object Links, and Sticker Placements remain distinct data and sticker placement does not modify base Card Characteristics.
- The repository currently has no application source, test suite, or established importer/data-model test seam. The agreed importer contract seam is new; there is no test prior art to follow.

## Out of Scope

- Executing, evaluating, or enforcing card abilities, effects, triggers, turn procedures, or characteristic derivation in the initial Manual Match.
- Full automated rules play in the initial release. Automation is staged separately while the data structures are established now.
- Scheduled imports, automatic background refresh, or live external card lookups during a Match.
- Deck construction legality, format legality, banlist enforcement, or permitting an unimported Card Definition in a Decklist.
- Gameplay differences between alternate printings of the same named card.
- Scheme or Vanguard variant procedures and lifecycle.
- Expanding sticker mechanics into base Card Characteristics.
