# Full catalog with staged rules coverage

The local Card Catalog targets the full Scryfall card pool and can be populated incrementally by importing one set at a time using its set code; the initial seed may contain a single set. Card data uses a comprehensive game-specific model for all known game-relevant characteristics and card forms rather than mirroring Scryfall's schema. In regular Magic, the card name defines Card Definition identity and same-named printings share that definition. Each Card Definition has one or more Card Components with the same characteristic field model and carries its Color Identity. Linked Alternative Characteristics records use the same field model for partial or full context-specific alternative values. Their composition mode states whether unspecified values inherit from the Card Component where the Comprehensive Rules leave them unchanged or are absent from a full alternative in its applicable context. Card Abilities share a structured representation with a kind and rules text, plus applicable trigger, condition, cost, mode, target, variable value, replacement or delayed behavior, effect, and references to relevant card data or Match context; keyword abilities such as flying, haste, and trample use the same representation. Characteristic-defining abilities remain static Card Abilities whose structured data declares the characteristics and value sources they define; printed stat values such as Tarmogoyf's `*` and `1+*` remain in Card Characteristics, without reverse references from the stat fields to the ability. This data is separate from executable behavior. Rules automation is not required for the first Manual Match; executable card rules can be added in later stages. All cards present in the local catalog remain usable in Manual Matches, while Rules-Automated Matches use only cards whose behavior is supported. Catalog availability remains separate from rules coverage, and the long-term goal is automated rules support for every card. The initial Match model represents special card/object types and the Zones or supplementary decks they need, melded objects composed from two Card Instances, manual attachments, and manual Object Links from source Game Objects to related Game Objects. These structures do not automate their mechanics. Automated tests are required as mechanics are added so each supported rule can be validated. Before implementation, validate the data model against user-selected card examples and refine it for any uncovered fields or forms.

The initial 100-card review is recorded in [`.scratch/multiplayer-manual-tabletop/card-model-review.md`](../../.scratch/multiplayer-manual-tabletop/card-model-review.md). The Match stores Object Links separately from attachments. One default Card Printing supplies stored characteristics for each Card Definition; gameplay differences between alternate printings are not modeled. Card Abilities can reference Color Identity and relevant Match context. A named choice is stored on its Game Object and may be any card name, whether or not a full Card Definition is locally imported. The full Card Name Directory is available from the initial release, separately from per-set Card Catalog imports and Decklist eligibility; alternate names can resolve to Alternative Characteristics. The shared Planechase area supports multiple active Plane Game Objects, including Spatial Merging. Additional card forms need explicit sample review before implementation.

The initial version does not provide variant-specific play support for Schemes or Vanguards. Their records may retain generic imported card information, but the model does not need Scheme Deck lifecycle or Vanguard setup modifiers. Sticker Sheets and Sticker Definitions are separate from card data; Matches relate available sheets to Match Players and placements to Game Objects without adding sticker fields to Card Characteristics. Conditional Card Ability structures preserve shared conditions, related abilities, and characteristic changes before any rules automation is implemented. Characteristic-defining abilities remain structured static Card Abilities that declare their characteristic outputs, while printed stat markers remain in Card Characteristics without reverse references to those formulas. Replacement and triggered Card Abilities reuse a typed Zone Change Condition for the affected object, source and destination Zones, and whether the move would occur or has occurred; reusable Object Filters separately describe which moving objects qualify. Filters remain eligibility predicates; characteristic-check timing, such as a pre-Zone-change view or last known information, belongs to the trigger, target, condition, or effect that uses the filter or characteristic. The replacement action and triggered effect remain distinct, and this does not add a Match event history. Continuous effects store precise typed changes, but card data does not duplicate Comprehensive Rules layer or sublayer labels; future rules automation derives those classifications from the changes' meaning. Active Continuous Effects remain separate from their recipients' printed Card Characteristics and retain source ability, affected objects, typed changes, duration, and applicability so that future rules automation can derive effective characteristics. Captured Copiable Values, including copy exceptions, use immutable records that copied Game Objects can share; each object's counters, status, attachments, and other Match state remain separate, and copies do not depend on the original object's later state.
